# Stage 17 タスク・キャンセルスコープの回収

タスクとスコープの管理を単調増加する配列から、終了時にエントリを削除するHashMapに変更。IDは単調増加のままとし、古いタイマーが別のタスクやスコープに適用されないようにする。タイマー・期限のヒープには無効な世代を整理する処理を追加。終了したPythonのCancelScopeはcancel_calledの状態を保存してランタイムへの参照を解放する。

## 長時間稼働を想定した反復試験

一つのrunで100タスクずつ1,000バッチ、計100,000タスクを生成・終了。各タスクで期限を10回変更してチェックポイントを通過する。Linux x86_64、CPython 3.12、Trio 0.35。各実装1回の診断測定。

| 指標 | Trio | Rust |
|---|---:|---:|
| CPU時間 | 2.951 s | 0.723 s |
| 100タスク終了時 RSS | 20,080 KiB | 19,752 KiB |
| 10,100タスク終了時 RSS | 20,284 KiB | 19,852 KiB |
| 100,000タスク終了時 RSS | 20,304 KiB | 19,852 KiB |

Rustのバッチ終了時の管理数は最終時点でタスク1、スコープ1、sleepタイマー0、期限ヒープ4。タスク1とスコープ1は実行中の親タスクと外側のスコープ。期限ヒープ4には無効化された登録を含む。最終バッチまで管理数が増え続けないことを確認。RSSはプロセス全体の測定で、単独の診断結果から全条件でリークがないとは判定できない。

## 600タスク比較（7ペア、同一CPU固定）

| 負荷 | Trio CPU中央値 | Rust CPU中央値 | ペア比中央値 |
|---|---:|---:|---:|
| チェックポイント | 108.51 ms | 31.24 ms | 3.42 |
| 600周期タスク | 195.13 ms | 18.39 ms | 10.41 |
| 580待機＋20周期タスク | 18.67 ms | 3.53 ms | 5.27 |
| 600待機タスク・キャンセル | 9.52 ms | 2.31 ms | 3.92 |
| 6,000期限キャンセル | 97.51 ms | 65.66 ms | 1.48 |

期限キャンセルはStage 16の28.42 msから65.66 msに増えた。別日の環境での測定であり、HashMapとキャンセル対象の全走査の費用が候補だが原因は個別に計測していない。次はキャンセル対象の索引と管理構造を見直す。管理領域の容量は同時タスク数の過去最大値に依存する。異常終了時の参照循環・リソース解放と全公式スイート、3.15、ARM64は未検証。
