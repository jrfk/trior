# Stage 16 CancelScopeの期限と動的shield

Rust側にキャンセル期限の最小ヒープを追加。期限の更新は世代番号で過去の登録を無効化する。期限切れのスコープをまとめてキャンセルし、待機中のタスクを起床させる。shieldを解除する場合も待機中タスクのキャンセル状態を再評価する。current_timeとsleep_untilの基本APIも追加。

Linux x86_64、CPython 3.12.14、Trio 0.35.0、Rust 1.100.0、PyO3 0.30.1。単一CPU固定、新規プロセス7ペア、実行順をシャッフル。各CPU時間は中央値、倍率はペア比の中央値。

| 負荷 | Trio CPU | Rust CPU | CPU速度比 |
|---|---:|---:|---:|
| 600タスク・60,000チェックポイント | 109.94 ms | 26.93 ms | 4.05 |
| 600周期タスク | 203.62 ms | 15.40 ms | 13.47 |
| 580待機＋20周期タスク | 17.25 ms | 3.07 ms | 5.71 |
| 600待機タスク・キャンセル | 9.84 ms | 1.75 ms | 5.63 |
| 600タスク・計6,000期限キャンセル | 104.47 ms | 28.42 ms | 3.72 |

混合負荷のCPU占有率中央値は8.23%対1.52%。周期タスクの起床遅延p99中央値は12.53 ms対0.44 ms。期限キャンセル試験では各タスクが10 msの期限付きスコープ内でsleep_foreverを待機し、キャンセル捕捉を確認する操作を10回繰り返す。

差分テスト20件通過。追加テストは期限による起床、期限解除・過去の期限への変更、動的shield解除、退場済みスコープの期限無効化。

未検証の互換性は残る。Clock、relative deadline、例外グループと複雑なキャンセル伝播、KI、guest mode、I/O、全公式テスト、3.15などは今後の対象。期限切れ処理やshield変更は待機タスクを走査するので、より大規模な負荷ではスコープ木と待機タスクの索引を検討する。タスクとスコープの管理領域はrun中に増え続け、長時間運転には再利用と参照解放の検証が必要。

再現方法はStage 15と同じ。bench_runtime.pyにdeadlines負荷を加えた。生データはruntime_comparison.json。
